# 本地 MCP 任务拆解与监察设计

> 历史方案，未按此实现。当前进度由内置 Runtime 的 `update_plan` 与 SQLite/SSE 执行卡提供，不向 `self.code.run` 增加 `steps` 或逐步启动 CLI。当前架构见 [项目架构](../../architecture.md)。

## 目标

让用户通过语音派给咚咚的编程任务可见、可跟踪：能看到灵矽拆出的步骤、当前正在做哪一步、哪些步骤已完成，以及最近的执行输出。

现有产品链路保持为：

```text
语音输入 -> 灵矽（理解、拆解） -> 本地 MCP（接收、调度、记录状态） -> code agent（执行）
```

灵矽是规划者，本地不再调用 CLI agent 生成第二份计划。MCP 对步骤做基本校验，不重新规划或自行判定目标完成。

## 方案

复用现有单任务和子进程机制，按灵矽提供的步骤串行执行。`self.code.run` 保留 `instruction`、`agent`、`cwd` 和 `wait_seconds` 的兼容行为，增加可选的 `steps` 数组。工具说明要求灵矽把多步任务拆成少量、可顺序执行的步骤，并在一次调用中传入；简单任务可传一个步骤。旧调用未提供 `steps` 时，把原指令作为单步执行。

每步单独启动一次现有配置里的 CLI agent，按顺序运行在同一个受 `resolve_dir()` 限制的工作目录中。每步 prompt 同时带上总目标、步骤序号和该步内容，要求只完成当前步骤。串行执行避免多个 CLI 同时修改同一工作树；每一步完成后保留其结果摘要，失败则停下后续步骤。

任务和步骤状态保存在当前进程内存中，沿用现有“重启清空”的行为。一次只允许一个活动任务。此版本不做 SQLite、并行 worker、子任务、自动重试或跨重启恢复。

## 状态与交互

任务状态：`running`、`done`、`blocked`、`stopped`。每个步骤状态：`pending`、`running`、`done`、`blocked`、`stopped`。任务快照至少包含任务 ID、目标、agent、工作目录、当前步骤、步骤总数、每步状态与结果摘要、运行时长和最近输出。

- MCP：`self.code.run` 立即返回任务 ID 和步骤概览；现有 `self.code.result` 按任务 ID 返回状态、步骤进度及输出；`self.code.stop` 停止当前步骤并将未开始的步骤标为 `stopped`。
- 面板：复用现有 `/state` 轮询，在当前任务区域列出步骤状态、`已完成 / 总数`、当前步骤与输出；派发后显示任务 ID。
- 监察由进程内状态和面板轮询完成。MCP 在 `self.code.run` 返回后不主动推送异步进度；灵矽需要在后续对话中调用 `self.code.result` 查询。

## 失败与兼容

步骤输入必须是非空字符串数组；拒绝空列表、空步骤和超出上限的计划。建议上限 8 步，避免单次语音派发产生过长队列。agent 启动失败或非零退出码时，当前步为 `blocked`，后续步骤不再执行，任务保留失败原因与输出。主动停止后，当前步和剩余步骤标记为 `stopped`；已有命令超时行为继续生效。

工作目录白名单、agent 配置和环境变量校验继续复用现有实现。步骤内容作为 prompt 参数传给 CLI，不经 shell 拼接。

## 范围与验证

改动预计触及 `agent.py`、`tools.py`、`state.py`、`panel.py`、`panel.html`、`tests/smoke.py` 和相关架构说明；不增加依赖。根据现有规则，在唯一的 `tests/smoke.py` 补充步骤输入校验、任务进度变化、失败停止后续步骤和 stop 边界的断言。

验收条件：

1. 灵矽传入 3 步后，本地立即返回同一任务 ID 和步骤列表，面板能显示 `0/3`。
2. 执行期间当前步骤变为 `running`，完成后变为 `done`，进度随步骤递增。
3. 某步失败后，任务显示 `blocked`，后续步骤不启动，失败输出可查询。
4. 停止活动任务后，不再启动新步骤，任务和剩余步骤显示 `stopped`。
5. 不带 `steps` 的旧式 MCP 调用仍可作为单步任务执行；越权目录和缺少 agent 环境变量仍被拒绝。

## 未包含

SQLite 持久化、多个任务并行、任务历史页面、MCP 服务端主动推送、规划质量评估、步骤间自动重试和对子任务的 DAG 编排。若以后需要任务在咚咚重启后继续，再单独设计持久化和恢复语义。
