# 通用任务机制 · 拆解 / 调度 / 监察

提炼自 OpenClaw 的 goal + subagent + swarm 三层，剥掉聊天产品的外壳，只留能移植的骨架。

配套代码：`model.py`（状态与 CAS）、`kernel.py`（三个循环）、`demo.py`（自证，跑到 `finished=True`）。

---

## 0 一句话

**把「任务管理」降级成「状态机 + 事件投递」：拆分交给调用者，可靠押在所有权记录上。**

它不提供 DAG，不提供工作流 DSL，不提供中心调度器，也不提供重试框架。

| 提供 | 不提供 |
| --- | --- |
| 目标 / 工作项二分 | 编排图、节点、连线 |
| CAS 抢占 + 六种状态 | 重试策略、回滚 |
| 有界快照（监察） | 轮询接口、看板 |
| 收口四闸门 | 汇报文案 |
| 四层预算 + 拒绝可见 | 限流器、熔断器 |

代价写在最后：没有流程图可重放，同一个任务两次跑法可能不同。

---

## 1 为什么是「目标 + 工作项」，不是「任务列表」

大多数自制 agent 的失败点就在这里：把「要做的事」和「算不算做完」混成一个 task 列表，于是

- 做完一项不等于目标推进一格（没有验收）
- 目标只能靠人看了说「好了」（无法自动收口）
- 重试会把同一行状态改来改去（结果被覆盖，历史丢了）

所以分成两种对象：

| | Goal | Work |
| --- | --- | --- |
| 是什么 | 要**证明**的命题 | 可**派发**的单元 |
| 关键字段 | `proof`（证据，非空才算 met） | `attempts`、`retry_of`、`result` |
| 状态 | open / met / abandoned | open / running / done / blocked / exhausted / stopped |
| 谁能改 | 只有规划者能 prove，且必须带证据 | 只有内核能改；执行者只能报结果 |
| 可否嵌套 | 是（`parent` + `depth`） | 通过 `goal_id` 挂到目标上 |

三条由此推出来的规则：

1. **work 做完不会自动让 goal 达成**，必须先 prove。`proof` 是字符串——写不出证据，说明这个目标当初就没想清楚。
2. **work 的终态不回退**。同一个目标没做完，是新建一个 work（`retry_of` 指向旧的），不是把旧的改回 open。
3. **`blocked` ≠ `done` ≠ `exhausted`**。三种终态，三种下游动作（见 §6）。

## 2 三个循环

```text
        ┌────────── 事件（结果回来 / 人改目标 / 心跳） ──────────┐
        │                                                        │
        ▼                                                        │
   调度循环 ── claim(CAS) ──> 执行者 ── Result ──> 结算 ────────┘
        │
        │ 空闲或有事件
        ▼
   规划循环  snapshot() ──> Decision ──> 内核按固定顺序落地
        │
        ▼
   监察      同一个 snapshot()，也喂给人看的那一侧
```

三者**只通过 Store 通信**，不共享可变对象：快照是拷贝，决策是纯数据。这是「可重启、可测试」的根——任何一环崩了，重启后从 Store 重建，不需要重放调用栈。

### 落地顺序是固定的

`Decision` 是一份纯数据，内核按这个顺序执行：

```text
kill → 加目标 → 加工作项 → prove → finish
```

先砍掉不该跑的（否则会多跑一轮），再加新活，最后才允许收尾（否则新活被收尾逻辑吞掉）。

**规划者不写库**，只返回决策。好处是同一份 snapshot + 同一个 Decision = 同一个结果；可回放、可 dry-run、可单测。

## 3 监察：有界快照，不是轮询

最容易做错的一层。三种做法：

| 做法 | 问题 |
| --- | --- |
| 执行者主动汇报 | 崩了就永远不报，父级不知道有东西在跑 |
| 父级轮询状态表 | 烧 token、烧 CPU，还会写出死循环 |
| **每轮注入一份有界快照** | 崩了也能从 Store 重建；成本固定 |

快照五段，每段有硬上限：

| 段 | 上限 | 用来判断 |
| --- | --- | --- |
| 目标 | 全部 open + 最近 met | 还差什么 |
| 排队 / 在跑 | 20 / 16 | 卡在哪、要不要加派 |
| 刚结束 | 8（按结束时间倒序） | 发生了什么 |
| **结果待消费** | 8 条 | 还有什么没告诉人 |
| 拒绝记录 | 8 条 | 想拆的为什么没拆成 |

三条硬规则：

1. **超上限只报计数，不报明细**。这不是省 token，是逼调用者知道「你派多了」——看不见明细，人才会去调预算，而不是假装看得见。
2. **快照里的文本是数据，不是指令**。`work.text` 可能来自用户或另一个模型，注入前必须转义（OpenClaw 的做法是 JSON 引用 + 字面量清洗）。
3. **「已完成」和「已交付」是两个状态**。合并会出两种事故：重启后重复汇报，或者结果被吞掉。所以内核有 `consume()`：汇报完才标记，标记后不再出现在快照里。

第 3 条最常被省掉，代价最大。一个反复汇报「任务完成了」的助手，比不汇报的更让人不信任。

## 4 收口：四道闸门

```text
① 叶子结算   执行者交回 Result → 内核按控制指令优先改终态
② 向上合成   父级只看到结果（不是子级的完整对话），决定 prove 还是加活
③ 续跑判定   一轮干净结束但目标还 open → 再来一轮
④ 目标 claim 全部 goal met → finish
```

### 闸门 ③ 的五个条件

少任何一条都会出事故：

```text
可以继续 = 本轮干净收尾（不是被中止 / 超时 / 还有未完成的工具调用）
        && 没有未结的子任务（否则父级会和子任务抢同一批结果）
        && 队列空（否则会插队）
        && 还有 open 目标
        && 没超预算
```

这是 OpenClaw 里 `isGoalContinuationOutcome()` 加两道检查的等价物。抄的时候**别省第 2 条**：最容易出的 bug 是父级在子任务还在跑时又续跑一轮，同一批结果被处理两次。

### 闸门 ④ 的权限拆分

| 角色 | 能做什么 |
| --- | --- |
| 执行者 | `done` / `blocked` / `exhausted` |
| 规划者 | 加目标、加工作项、`prove`（必须带证据） |
| 内核 | 改状态、抢锁、结算、收尾 |
| **人** | 暂停、恢复、放弃、改目标、叫停单项 |

模型**不能**自己把目标标记成完成——它只能「证明」，能不能收工由闸门 ④ 判。这不是不信任模型，而是因为「自我宣告完成」是唯一无法从外部证伪的错误。

## 5 六条不变量

改任何实现之前，先确认这六条还成立：

1. **一个工作项只有一个 claim 者**。claim 是 CAS，`attempts+1`，抢不到就跳过（不排队、不等待）。
2. **一个结果只有一个交付者**。交付状态不可回退：`pending → 已交付`，重启不得重放已交付的。
3. **控制优先于执行者自述**。叫停到达后，执行者返回 `done` 也被记成 `stopped`。
4. **失败不自动重放**。重试 = 新建一项 + `retry_of`；要限次数就沿 `retry_of` 链计数，别在状态里记「重试次数」。
5. **状态变更只有一个入口**（Store）。规划者、执行者、人都是这个入口的调用方，谁都不能直接写字段。
6. **终态不复活**。要重做就新建。历史是拿来读的，不是拿来改的。

## 6 预算与失败语义

四层预算，四种不同的失败味道：

| 预算 | 防的是什么 | 默认 |
| --- | --- | --- |
| `max_depth` | 目标无限嵌套 | 3 |
| `max_children` | 一个目标塞爆子项 | 8 |
| `max_inflight` | 并发打爆模型 / 工具 | 4（按机器调） |
| `max_total` | 整轮失控 | 200 |
| `max_rounds` | 循环不收敛 | 1000 |

**被拒绝必须可见**。内核的 `_refuse()` 会往快照里记一条 `refusals`。`demo.py` 里就真出过一次：根目标下 8 个子项后，「写交接单」被拒。若静默丢掉，调用者会以为已经拆了，然后盯着一个永远不动的目标。

四种终态，四种下游动作：

| 终态 | 含义 | 谁处理 | 怎么处理 |
| --- | --- | --- | --- |
| `done` | 做完了 | 规划者 | 可能触发 verify / prove |
| `blocked` | 出错，方向可能就不对 | **人** | 看原因，换方案（新建项，不带 `retry_of`） |
| `exhausted` | 方向对，预算 / 时间不够 | 规划者 | 拆小（新建项，带 `retry_of`） |
| `stopped` | 人叫停，或整轮收尾 | 不需要 | 不进验收条件 |

这张表的用处：代码里出现 `if state == "failed"` 时，你就知道模型漏了一种情况。

## 7 落到 dongdong

一句话 → 目标 → 工作项 → codex 子进程：

```text
用户："把交接资料补齐"
  └─ goal: 交接资料已补齐
       ├─ work: 读目录          → SubprocessRunner(["codex","exec", ...])
       ├─ work: 读构建脚本
       ├─ work: 读测试          → blocked（目录不存在）
       └─ 规划者换方案 → work: 读测试（换目录）→ done
     prove(goal, "五个来源读过 + 冒烟可跑")
     finish
```

| 机制里的角色 | dongdong 里是谁 |
| --- | --- |
| Planner | 一次 LLM 调用：输入快照，输出 Decision（JSON） |
| Runner | `SubprocessRunner`：一项 → 一个 codex / claude 子进程 |
| Store | SQLite（`~/.dongdong/tasks.db`），重启后接着跑 |
| 人 | 面板上三个按钮：看进度、停、继续 |

人只有三个动作，别加第四个。多一个动作就多一条状态路径。

## 8 什么不做

对齐本仓库的黑名单，这些一律不加：

- **不做 DAG / 工作流 DSL**：编排要么是程序，要么是模型的决策；中间格式只会变成两边都不认的第三种语言
- **不做中心调度器的轮询 loop**：事件驱动，`tick()` 是给测试用的，不是给 sleep 用的
- **不做跨进程消息总线**：Store 是唯一真相，多一个通道就多一份不一致
- **不做 planner 插件注册表**：一个 Planner 协议足够
- **不做自动重试框架**：重试是规划者的决策，不是框架的行为
- **不做每项都写审计日志**：只记终态 + 证据 + 拒绝原因

## 9 怎么验收

不看代码，看这五条行为：

```text
1. 一项 exhausted → 规划者能看到，且不自动重跑同一项        ✅ demo
2. 一项 blocked   → 换方案是新建项，旧项保持 blocked 可见    ✅ demo
3. 杀进程重启     → 在跑的项变回 open 或 stopped，不重复派发  ⬜ 需 SQL Store
4. 人叫停         → 排队项立刻 stopped，不进验收条件         ✅ demo
5. 目标全 met     → 不再派发任何新项，finished=True          ✅ demo
```

第 3 条是唯一必须先换持久化才能验的。内存 Store 上它必然通过（进程没了状态也没了），所以别用内存实现糊弄过去。

跑一遍：

```bash
.venv/bin/python design2/demo.py
```

期望最后一行是 `收尾：finished=True  reason=全部目标达成`。

## 10 与 design/ 的关系

`design/kernel/`（567 行，ARTEX 风格）是上一版：有 Goal / Item / Event / Decision / Result，但缺 `scheduler.py`，也没有监察层和文档。

这一版补的正是它缺的三块：**有界快照 + 交付状态机 + 收口闸门**，并把五个文件收成三个。两者可以合并——把 `kernel.py` 的 `snapshot()` 和 `consume()` 挪进 `design/kernel` 即可，数据模型是同一个思路，不冲突。
